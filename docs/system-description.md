# MedHub описание системы и направления развития

Состояние на 30 сентября 2026 года.

Документ описывает фактическую реализацию MedHub и может использоваться как основа для дальнейшего ТЗ или передачи проекта другому разработчику. Описание текущих возможностей отделено от ограничений и предлагаемых улучшений. Значения секретов не включены.

**Кратко:** MedHub — работающий MVP медицинского писаря. Он превращает аудиозапись консультации в структурированный черновик, который врач редактирует, подтверждает и выгружает в DOCX. Распознавание и генерация проверены на загруженной пользователем записи. Интеграция с настоящей МИС пока не реализована.

## 1 Назначение и границы продукта

Основная задача — сократить время заполнения медицинской документации после приёма.

Система помогает:

- записать разговор или загрузить готовое аудио;
- получить транскрипцию;
- замаскировать распознанные персональные данные перед внешней обработкой;
- извлечь сведения в структуру выбранной формы;
- проверить и исправить результат;
- выбрать код МКБ-10;
- подтвердить документ и скачать заполненный бланк.

Принцип работы: **AI готовит черновик; медицинское решение и подтверждение остаются за врачом.**

Сейчас это не полноценная МИС. Здесь нет расписания приёмов, полноценной карточки пациента, лабораторной системы, биллинга, электронных рецептов или электронной подписи.

## 2 Фактическое состояние запуска

| Компонент | Состояние на дату описания |
|---|---|
| Интерфейс | Локальный Vite-сервер, `http://localhost:5173` |
| API | FastAPI, `http://127.0.0.1:8000` |
| Режим приложения | `APP_MODE=live` |
| Генератор документов | `LLM_PROVIDER=openai` |
| Модель генерации | `gpt-4.1-mini` |
| Распознавание | Локальный faster-whisper, модель `small` |
| Вычисления распознавания | CPU, `int8` |
| База данных | SQLite |
| Аудиохранилище | Локальная папка |
| Передача в МИС | Только MockMIS |
| Формы документов | Шесть DOCX-шаблонов |
| Максимальный размер аудио | 50 МиБ |
| Срок хранения аудио | По умолчанию 7 дней |

Важное различие: **`live` включает реальные обработчики и проверки конфигурации, но само по себе не делает установку готовым продакшеном.** HTTPS, резервное копирование, эксплуатационная безопасность и полноценная интеграция с МИС — отдельные задачи.

Установленный по запросу владельца простой пароль врача перед публичным запуском необходимо заменить.

## 3 Архитектура

Система построена как модульный монолит: один сервер приложения с отдельными модулями для распознавания, маскирования, генерации, документов и экспорта.

```text
Браузер врача
    │
    │ REST API + JWT
    ▼
FastAPI
    ├── Авторизация и доступ к консультациям
    ├── Управление состояниями консультации
    ├── Локальное хранение аудио
    ├── Whisper → транскрипция
    ├── PII Guard → маскирование
    ├── OpenAI → структурированный черновик
    ├── Проверка, правки и подтверждение
    ├── Генерация DOCX
    └── MockMIS

Хранение состояния и документов: SQLite / PostgreSQL
```

Во внешний OpenAI передаётся текст после маскирования и описание полей выбранной формы. Сам аудиофайл туда не отправляется.

## 4 Пользовательский сценарий

### Создание консультации

Врач указывает внешний идентификатор пациента и выбирает форму.

Отдельной таблицы пациентов нет. `external_patient_id` — ссылка на пациента во внешней системе, а не полноценная медицинская карточка.

По умолчанию выбирается «Осмотр терапевта».

### Получение аудио

Доступны два способа:

- запись через микрофон;
- загрузка файла WebM, WAV, MP3 или M4A.

Интерфейс проверяет размер и формат. Сервер повторно проверяет размер, MIME-тип и сигнатуру файла.

Запись отправляется после остановки. Потокового распознавания во время разговора сейчас нет.

### Распознавание

Whisper обрабатывает файл локально. Сохраняются:

- исходный текст;
- язык;
- длительность;
- сегменты с временными отметками;
- название модели.

Разделения на врача и пациента пока нет: поле `speaker` предусмотрено, но распознаватель его не заполняет.

### Подготовка текста

Нормализация сейчас консервативная: удаляются лишние пробелы и пустые строки.

Она не исправляет медицинские термины, не восстанавливает дозировки и не превращает произнесённые словами числа в измерения.

После этого выполняется маскирование персональных данных.

### Генерация

OpenAI получает подготовленный текст и структуру выбранного бланка.

Инструкции требуют:

- извлекать только явно сказанное;
- не придумывать диагнозы, назначения и показатели;
- оставлять отсутствующие сведения пустыми;
- не воспринимать напечатанные в бланке варианты нормы как факты о пациенте;
- не назначать код МКБ-10.

Это ограничения запроса и валидации, а не гарантия медицинской правильности ответа.

### Проверка и подтверждение

Врач исправляет поля, выбирает код МКБ-10 и сохраняет проверку.

Затем отдельно подтверждает документ. После подтверждения редактирование и повторная генерация через текущий API запрещены.

DOCX становится доступен только после подтверждения.

## 5 Состояния консультации

Основной путь:

```text
CREATED
  → RECORDING
  → PROCESSING
  → TRANSCRIBED
  → PROCESSING
  → AI_GENERATED
  → REVIEWED
  → APPROVED
  → SENT_TO_MIS
```

`FAILED` обозначает ошибку обработки. Повторное действие зависит от того, сохранились ли аудио и транскрипция.

Важные правила:

- загрузка файла переводит консультацию в `RECORDING`;
- распознавание и генерация используют общий статус `PROCESSING`;
- сохранение документа переводит его в `REVIEWED`;
- подтвердить можно только сохранённую проверенную версию;
- подтверждённый документ нельзя изменить;
- повторный экспорт возвращает прежний результат без создания нового mock-экспорта.

Есть защита от сохранения устаревшей версии: клиент передаёт номер `version`, сервер при конфликте возвращает `409`.

**Ограничение:** `REVIEWED` означает факт сохранения через интерфейс, а не доказательство, что врач прочитал каждое поле.

## 6 Модель данных

В базе семь основных таблиц.

| Таблица | Назначение |
|---|---|
| `users` | Пользователи, роли, имена и хеши паролей |
| `consultations` | Пациентский идентификатор, форма, состояние, создатель и подтверждение |
| `audio_files` | Ссылка на локальный файл, формат, размер, время загрузки |
| `transcripts` | Исходный, нормализованный и маскированный текст, сегменты и модель |
| `consultation_documents` | AI-черновик, рабочая версия, утверждённые данные, модель и номер версии |
| `consultation_edits` | Изменения отдельных полей относительно AI-данных |
| `mis_exports` | Результаты экспорта и идентификатор документа |

Структурированные клинические данные хранятся в JSON; для PostgreSQL предусмотрен JSONB.

### Структура медицинского документа

Общие поля:

- `complaints` — жалобы;
- `anamnesis_morbi` — анамнез заболевания;
- `anamnesis_vitae` — анамнез жизни;
- `allergies` — аллергии;
- `medications` — принимаемые препараты;
- `vital_signs` — показатели;
- `objective_status` — объективный статус;
- `diagnosis` — текст диагноза;
- `diagnosis_code` — выбранный врачом код;
- `recommendations` — рекомендации;
- `prescribed_medications` — назначения;
- `additional_notes` — дополнительные сведения;
- `template_fields` — поля конкретной специальности.

Для препаратов предусмотрены название, дозировка, частота и длительность приёма.

Показатели включают температуру, давление, ЧСС, ЧДД и сатурацию. Сейчас они представлены строками: отдельной модели числовых значений и единиц измерения нет.

Контракт: [schemas.py](../backend/app/schemas.py).

Хранение: [models.py](../backend/app/models.py).

### Ограничения истории

Сохраняется AI-версия, относительно которой фиксируются правки. Однако повторная генерация до проверки заменяет этот AI-снимок. Полного неизменяемого архива всех генераций нет.

Журнал правок также пока не содержит отдельного автора каждой правки и полной последовательности всех действий пользователя.

## 7 Шаблоны документов

Поддерживаются:

1. Осмотр терапевта.
2. Первичный осмотр врача терапевта.
3. Первичный осмотр кардиолога.
4. Осмотр педиатра.
5. Осмотр проктолога.
6. Первичный осмотр хирурга.

Исходники находятся в [templates](../templates).

Для каждого шаблона заданы:

- стабильный идентификатор;
- название;
- общие и специализированные поля;
- нейтральные подписи;
- соответствие полей абзацам DOCX.

При экспорте используются утверждённые данные. Отсутствующие сведения обозначаются как «Не указано». Подпись врача автоматически не проставляется.

Реализация: [forms/__init__.py](../backend/app/forms/__init__.py).

**Важные ограничения:**

- сопоставление привязано к структуре и номерам абзацев исходных файлов;
- изменение DOCX может потребовать изменения адаптера;
- редактора шаблонов в интерфейсе нет;
- PDF-экспорт в приложении не реализован;
- готовый DOCX генерируется при скачивании, а не хранится как неизменяемый подписанный артефакт;
- версия и хеш шаблона пока не фиксируются в консультации.

Поэтому утверждённые данные защищены от правок, но изменение исходного шаблона потенциально изменит последующий вид скачиваемого документа.

## 8 Справочник МКБ-10

Используется предоставленный CSV:

[ref_disability_diagnoses_202609301227.csv](../seed/ref_disability_diagnoses_202609301227.csv).

В справочнике 14 380 уникальных кодов.

Поиск работает:

- по коду;
- по русскому названию;
- по казахскому названию.

Код выбирает врач. Он не заменяет свободный текст диагноза и переносится в утверждённую версию, DOCX и данные экспорта.

CSV загружается в память и кешируется. Это не отдельная управляемая справочная подсистема.

В исходных данных обнаружено расхождение RU/KZ для `J20.9`. Поэтому справочник нельзя считать проверенным только потому, что он успешно импортируется. Нужны проверка содержимого, версия и процедура обновления.

## 10 Безопасность и персональные данные

### Что реализовано

- JWT с ограниченным сроком действия — 8 часов.
- Хеширование паролей Argon2.
- Проверка роли пользователя.
- Врач видит свои консультации; администратор имеет расширенный доступ.
- Валидация клинической структуры и полей шаблона.
- Проверка размера и типа аудио.
- Защита локального хранилища от обхода путей.
- Маскирование текста перед OpenAI и повторная проверка на границе обработчика.
- API-ключ используется только сервером.
- Возможность загрузки секретов из файлов.
- Подготовленные Nginx-настройки HTTPS и защитных заголовков.

JWT хранится в памяти приложения и `sessionStorage`, а не в HttpOnly-cookie.

### Как работает маскирование

Локальные регулярные выражения ищут ИИН, телефоны, email, некоторые формы ФИО, адресов, дат рождения и документов.

Распознанные значения заменяются маркерами вроде `[PERSON_1]`.

Но это эвристический фильтр, а не гарантия анонимности. Ошибки распознавания, нестандартные имена, цифры словами и косвенные идентификаторы могут остаться.

Кроме того, исходный немаскированный текст сохраняется в локальной базе. Маскирование внешнего запроса не обезличивает всё хранилище.

### Чего пока нет

- ограничения попыток входа;
- MFA;
- управления сессиями и их принудительного отзыва;
- автоматического отзыва JWT при смене пароля;
- полноценного журнала чтения и выгрузки медицинских данных;
- шифрования данных на уровне приложения;
- реализованной процедуры резервного копирования и восстановления;
- разграничения по клиникам и организациям;
- пользовательского процесса согласия на запись и внешнюю обработку.

Стойкие пароли, ограничение попыток входа и MFA — приоритетные меры для публичного доступа. Они соответствуют рекомендациям [OWASP по аутентификации](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

## 11 Обработка задач и эксплуатация

Сейчас распознавание и генерация выполняются внутри процесса API.

Whisper запускается в отдельном потоке, но HTTP-запрос ожидает итоговый результат. В браузере статус `PROCESSING` опрашивается каждые две секунды.

При первом распознавании модель скачивается и загружается. Отдельного индикатора этих этапов нет.

После перезапуска API незавершённые `PROCESSING` переводятся в `FAILED`, чтобы действие можно было повторить. Из-за такого механизма восстановления текущую схему нельзя без доработки запускать в нескольких независимых экземплярах.

### Хранение аудио

Очистка запускается при работе приложения и затем примерно раз в сутки:

- удаляет аудио старше установленного срока;
- пропускает обрабатываемые консультации;
- не удаляет транскрипции и документы.

Политики срока хранения медицинских текстов пока нет.

### Ошибки и диагностика

Пользователю выдаются безопасные общие сообщения. Однако подробные технические причины во многих местах теряются.

Именно это затруднило диагностику несовместимости PyAV и отказа демогенератора. Несовместимость декодера была исправлена ограничением зависимости PyAV диапазоном `>=18,<19`; доступ к реальной генерации настроен отдельно через `LLM_PROVIDER`.

Нужны структурированные коды ошибок, идентификаторы задач и длительности этапов. При этом нельзя писать в технические логи ключи, токены и полный медицинский текст. Это соответствует рекомендациям [OWASP по журналированию](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

`/health` сейчас показывает конфигурацию, но не доказывает доступность OpenAI, готовность Whisper и исправность всех зависимостей.

Режим приложения и генератор разделены:

| Настройки | Поведение |

| `live` + `auto/openai` | Настроенный пароль врача, реальный OpenAI |

MockMIS остаётся заглушкой во всех этих вариантах.

Для локального запуска с текущими настройками важно явно загружать `.env`. Команда выполняется из корня проекта:

```bash
.venv/bin/python -m uvicorn app.main:app \
  --env-file .env \
  --host 127.0.0.1 \
  --port 8000 \
  --no-access-log
```

Docker-конфигурация содержит три сервиса: Nginx, API и PostgreSQL. Предусмотрены постоянные тома и подключение шаблонов/справочника только для чтения.

Файлы: [compose.yaml](../compose.yaml), [README.md](../README.md).
